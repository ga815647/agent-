# Remote Studio — candidate role and event contract

Status: proposal plus implementation candidate. Not selected by BOOTSTRAP or CONTROL_RELEASE. Existing O/BRAIN/W and Runtime Entry obligations remain effective until separately accepted promotion.

## Goal

The owner revised the product target: improve Chat's understanding, responsiveness and resistance to conversational momentum, doing useful work within available capability. A full mobile Codex experience is no longer the acceptance criterion. See `CONVERSATION-ASSIST-CANDIDATE.md` for the immediate caller integration. Existing durable task mechanics below remain optional support for longer work, not prerequisites for improving conversation.

## Responsibilities

- The chat entry submits the original request and project/task identity, and displays an acknowledged task ID or an honest delivery failure. It need not pre-solve the task. Missing tool invocation is still possible; this contract does not claim platform interception.
- A remote cognitive lead proposes an interpretation against persisted goals, constraints, explicit decisions and original events. It challenges one material goal/means mismatch or unresolved scope ambiguity; it does not infer new authority from suggestions, uncertain assent, or source documents.
- The trusted controller binds an accepted versioned contract. Model output cannot change that binding, grant authority, amend trusted executable commands, or approve its own result.
- The implementation Worker produces a candidate plus actual validation evidence. Localized repair can retain Worker context; uncertain framing/root cause merits fresh audit. A reviewer remains an evidence source, not a substitute implementation owner.
- O retains existing evidence-acceptance and formal commitment authority in this candidate. The proposed remote cognitive lead is not a hidden transfer of O authority. User questions are reserved for unresolved decisions, not bookkeeping.

## Event and continuity contract

An acknowledgement means the original event was durably stored, not that the job completed. Duplicate event identity with different content is rejected. New user events invalidate stale plans/results until interpreted; a process already in flight must be joined or reconciled before replacement work can start.

The durable task contract includes goal, source identity, scope, acceptance and authorized effects. Summaries are indexes, not replacement authority for original requests. Continuation uses task/version/candidate evidence and does not claim to restore hidden model reasoning.

A timed-out attempt with uncertain effects is ambiguous, not an automatic retry opportunity. Independent review is bound to the exact candidate/version. A reviewed deliverable does not imply merge, deployment or project-truth acceptance.

## Reconsideration and challenge

Retain the current goal/means and reconsideration principles. A preference such as accepting a larger graph is not a command to build one. Explicit approval closes the current decision unless new material evidence arises. Explicit changed goals supersede old plans; anti-momentum must not become resistance to the user.

Mechanical state guards enforce when a returned challenge pauses execution. They cannot guarantee that a model notices every meaningful conflict. Evaluate actual misunderstandings caught, unnecessary objections, task correctness, rework and human effort; never use reasoning length or challenge count as a quality proxy.

## Data and capability boundary

Private repository visibility alone does not classify every source file as confidential. An owner may consent to their own code/research being processed under a selected model's data-use terms. That consent does not admit credentials, third-party restricted material, unrelated personal content or unsupported executor capabilities. Machine-readable owner preferences and actual provider/harness eligibility belong to the private execution plane.

## Proposed delivery change, not active behavior

The target is event-based task acknowledgement/status rather than waiting for all work in each chat turn. Changing the existing every-turn Runtime Entry final receipt rule requires a separate control promotion. This candidate does not bypass it or call it solved.

The private candidate provides task storage, original-message context, fenced attempts, bounded harnesses and durable coding patches. Authenticated mobile ingress, background service recovery, production capability placement and recipe-specific MON-A effect handling require separate integration evidence. Existing accepted components should be reused; no general graph framework is required by this contract.
